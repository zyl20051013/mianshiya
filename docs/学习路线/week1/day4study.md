# 边做边学笔记

q：为啥要加pagesize限制

a：如果有个黑客，自己写了个脚本，故意传 `{"pageSize": 1000000, "current": 1}`。你的代码如果不管，数据库就会去硬盘里捞 100 万条数据，瞬间塞满服务器的内存，导致网站直接死机（这叫 OOM 内存溢出）。


N+1问题

a：“N+1 问题是指在查询主表数据（1次查询）后，在循环中逐条查询关联表数据（N次查询），导致数据库交互次数飙升，严重影响性能。
在我的项目里，查询题目列表需要显示用户信息。我采用的是 **‘批量查询 + 内存拼装’** 的方案。先收集所有题目的 userId 并去重（Set），然后通过 `listByIds` 一次性查出所有用户（1次查询），最后在内存中利用 Map 进行数据的匹配和填充。这样把 N+1 次查询降到了固定的 2 次查询，极大减轻了数据库压力。”


关于全局索引搜索问题

1. **猜想 1：使用 Elasticsearch（ES）**。
   ES 的核心是“倒排索引”。它就像一本书后面的“名词索引”，直接告诉你“JVM”这个词在第 5、12、89 页。它天生就是为了解决这种模糊搜索的，这也是你项目第二阶段要干的事。
2. **猜想 2：如果非要用 MySQL，怎么优化？**
   可以给字段建“全文索引（Full-Text Index）”，然后用 `MATCH AGAINST` 语法。但 MySQL 的全文索引对中文支持比较差，还需要装分词插件，不如 ES 方便。
3. **猜想 3：数据量小的时候先忍着**。
   如果现在总共只有几百条题，全表扫描也就几毫秒，不需要过度设计。但要在代码或文档里备注好，数据上了十万级就得换方案。
