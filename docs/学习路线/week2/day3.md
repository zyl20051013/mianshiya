# 手写签到接口

## 自测题

### 面试官提问 1：为什么用户 id 不能从前端传？

a:前端请求参数会被用户篡改，如果用前端传userId，恶意用户可能会传入别人的userId实现伪造其他同学签到

+：用户ID应该从服务端（登录token解析获得） ，避免越权操作

### 面试官提问 2：重复签到为什么返回 true？如果业务要求 "一天只能签一次，重复报错"，怎么改？

a：为了保证接口的**幂等性**。在网络波动导致前端自动重试，或用户狂点按钮时，接口多次调用和执行一次的效果相同。返回 `true` 代表“当前状态是已签到”，这样前端可以直接安心刷新 UI，不用去处理复杂的错误分支。


### 3. 查询时为什么先 `asBitSet()`，而不是循环 `get()`？

a：**循环 `get()`**：如果一年 365 天都有记录，会产生 365 次 Redis 网络请求（RTT）。如果在高并发下，这会严重拖垮系统性能。

**`asBitSet()`**：Redisson 底层使用 `GET` 命令或者 `BITFIELD` 命令将整个 Bitmap 一次性拉取到本地内存，转换为 Java 的 `BitSet` 对象。之后在本地内存中通过 `nextSetBit` 遍历，速度极快（纳秒级），且**只有一次网络请求**。


### 4. 返回“第几天”而不是“日期”，好处是什么？坏处是什么？

a：

1. **极简存储与传输**：后端不需要做 `LocalDate` 到 `String` 的格式化，直接返回 `[309]` 这样一个数字数组，数据量极小。
2. **展示层解耦**：后端只提供原始数据，前端拿到“第几天”后，结合选中的 `year` 参数，可以自由地将其渲染成日历热力图、列表或者转换为任何本地化时间格式。
3. **天然有序**：通过遍历 BitSet 拿到的索引天然是从小到大排列的，前端可以直接使用。


### 5. 如果明年要看 2025 年的记录，代码需要改吗？

a：

**不需要改代码，但需要注意数据一致性。**

代码中 `RedisConstant.getUserSignInRedisKey(year, userId)` 已经将年份作为参数传入，所以查 2025 年记录的请求会自动落到 `user:signins:2025:userId` 这个 key 上。

**延伸思考：**

* 如果 2025 年对应的 Redis Key 在过期时间（TTL）设置上不小心被清除了，那记录就会丢失。一般签到记录建议**永久保存**或至少保留多年。
* 如果时间跨度极大（比如查 2000 年的记录），只要 key 没被删且当年的 `offset` 逻辑正确，依然能正常查出。
