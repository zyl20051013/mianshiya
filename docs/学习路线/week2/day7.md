# 数据同步与闭卷挑战

## 自测题

### 面试官提问 1：为什么增量同步要绕过逻辑删除？

a:因为用MyBatis_Plus,会在条件默认加 WHERE isDelete = 0 ,就查不到 = 1的数据，导致MYSQL里面改了，但是ES不更改，搜索会有幽灵数据，不准确

+：解决方法：所以我们需要在 Mapper 层手写原生的 `@Select` SQL，绕过框架的逻辑删除拦截，把那些 `isDelete = 1` 的数据也抓取出来推给 ES。

### 面试官提问 2：已删除的题目在 ES 里是怎么“消失”的？

a:在 ES 里，它并没有被真正“消失”或物理删除。
增量同步任务会把这条被逻辑删除的数据重新推送到 ES（因为主键 ID 相同，所以是覆盖写入），只是此时这条文档的 `isDelete` 字段的值变成了 `1`。
而在我们前端的搜索接口中，`BoolQuery` 必定包含一个 `filter` 条件：`termQuery("isDelete", 0)`。所以当用户搜索时，`isDelete=1` 的文档会被直接过滤掉，从而达到“消失”的效果。这也是搜索引擎常用的同步策略——**改标记，不删文档**。


### 面试官提问 3：为什么用“近 5 分钟”而不是“上次同步时间”？

a：因为网络延迟、定时任务阻塞、或者服务器时钟微调等不可控因素，如果严格使用“上次同步时间”作为起点，极容易造成**漏查**。
如果多查一点（比如往前推 5 分钟），由于我们的写入是基于 ID 的覆盖写入（幂等操作），哪怕数据重复同步几次，也绝不会产生脏数据。**宁可多查一点做无用功，也绝对不能漏查一条数据**。这是数据同步任务可靠性的基石。


### 面试官提问 4：双写为什么要先写 MySQL？

a:因为 **MySQL 是主库（唯一真相来源）**。
如果我们先写 ES，ES 写成功了，但随后写 MySQL 失败了（比如超时），那么就会导致 MySQL 里没有这条数据，而 ES 里却有一条脏数据，从此产生了数据不一致。
相反，先写 MySQL 成功，哪怕紧接着写 ES 失败或者网络抖动，数据至少在主库里是安全的。ES 的缺失可以通过后续的定时补偿机制（或 MQ 重试）把数据同步过去，从而保证系统的**最终一致性**。


### 面试官提问 5：定时同步延迟 1 分钟，用户能接受吗？什么业务不能接受？

a:

对于大部分业务（比如面试刷题网站、内容管理系统），用户发了一道新题或删了一道旧题，晚 1 分钟才在搜索结果里生效，这是**完全可以接受**的，也不会影响核心体验。

**不能接受的业务场景**：

1. **电商秒杀/商品上架**：如果运营刚上架一个商品，用户搜索不到，可能直接导致业绩损失。
2. **金融/股票交易**：一秒的延迟都会导致严重的资金损失。
3. **实时聊天/消息推送**。
   对于这类要求**准实时（毫秒级）**的场景，必须使用 **Canal 监听 MySQL binlog** 或 **MQ 异步双写** 来替代定时同步。
