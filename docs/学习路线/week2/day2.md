# Redis与BitMap

## 自测题

### 面试官提问 1：为什么 offset 用“一年中的第几天”，而不是“时间戳”？

a：因为时间戳太长了有10位数，但是用一年中的第几天，只需要366个格子（格子的意思就是1/0）大概366/8个字节，如果要表示第几年，user:signins:年份:用户id

+：这体现了一种**业务映射**的思想。结合具体的业务边界（一年最多 366 天）来设计数据结构，而不是滥用底层系统提供的时间戳。

### 面试官提问 2：BitMap 一年 365 天占多少字节？100 万用户呢？

a: 一年最多 366 天，也就是 366 个 bit。因为 1 个字节等于 8 个 bit，所以 366 / 8 约等于 **46 个字节**。
100 万个用户，就是 100 万 × 46 字节 ≈ **46 MB**。

### 面试官提问 3：`RBitSet` 和 `BitSet` 该在什么时候用哪个？

a:RBitSet在Redis服务端，每次访问可能都会带有一次访问请求，适合单次访问

BitSet在JVM本地内存，操作极快，适合遍历和计算

！！！：重点：所以正确的姿势是：写入用 `RBitSet.set()`；读取时先用 `asBitSet()` 把数据一次性拉到本地变成 `BitSet`，再在本地用 `nextSetBit()` 遍历，**绝对不能用 `for` 循环去循环调 `RBitSet.get()`**。

### 面试官提问 4：重复调用签到接口会发生什么？为什么这么设计？

a：会触发幂等性校验，就是if（!RBiSet.set(offset)）

### 面试官提问 5：如果要求“打卡后 30 天内可撤销”，BitMap 还合适吗？

a:因为 BitMap 的操作是极其灵活的。如果要撤销第 X 天的打卡，只需要把第 X 位的 bit 从 `1` 改为 `0` 即可。
只需要在业务代码里加个判断：判断当前日期距离打卡日期是否在 30 天内，如果是，就允许调用 `set(offset, false)` 取消打卡。这不会破坏 BitMap 的底层结构。
