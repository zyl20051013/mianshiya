## 订阅变更

### 第一种：MQ（消息队列）订阅 —— 经理传话

* **怎么做**：你在代码里存完 MySQL 后，往 RabbitMQ 或 Kafka 里发一条消息：“1 号题目的标题改了，快去更新 ES！” 然后专门有个程序去监听这个消息队列，收到消息就去更新 ES。
* **优点**：实时性高，代码解耦。
* **缺点（致命痛点）**：**代码侵入太强！** 你必须在所有修改数据库的地方，都加上“发消息”的代码。万一哪天新来的实习生写了个更新 SQL，忘了发消息，数据就不一致了。

### 第二种：监听 binlog —— 派个卧底（大厂标配：Canal）

这就是业界大名鼎鼎的 **Canal** 方案（阿里开源的）。

**🧐 什么是 binlog？**
MySQL 有一个极其重要的底层机制：只要你执行了增删改操作，它就会在暗处（硬盘里）记一篇“日记”（binlog），记录下你改了什么。

**🕵️ Canal 是怎么干活的？**

1. **伪装成小弟**：Canal 这个组件，会伪装成 MySQL 的一个“从库（Slave）”。它告诉 MySQL：“老大，我是你的备份库，你把你的日记（binlog）实时同步给我吧。” MySQL 信以为真，就把日记源源不断地发给 Canal。
2. **翻译日记**：Canal 拿到日记后，一看：“哦，原来刚才有人把 1 号题库删了。” 它立刻把这个动作翻译成一条消息，发给消息队列（或者直接调用接口）。
3. **同步 ES**：你的同步程序收到消息后，立刻去更新 ES。

如果之后我做的项目后面尽量使用一下第2个，让自己的项目看上去更高大尚一些吧



4种方案分析


| 方案                              | 大白话解释                                                          | 优点                                                             | 缺点（致命痛点）                                                              | 适用场景                                       |
| --------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------- |
| **双写**                          | 在代码里，存完 MySQL 紧接着存 ES。                                  | 实时性极高（毫秒级）。                                           | 代码侵入强；如果网络一抖动，ES 写失败了，数据就不一致；且很难保证分布式事务。 | 数据量极小，且对一致性要求不极端的场景。       |
| **定时同步**（**本项目**）        | 定时任务每隔 1 分钟扫一下 MySQL 的`updateTime`，有更新的就推给 ES。 | 代码解耦；有兜底（哪怕 ES 挂了，重启也能补数据）。               | 有延迟（分钟级）。                                                            | 对实时性要求不高，允许用户晚几十秒搜到新数据。 |
| **Canal 监听 binlog**（大厂标配） | 伪装成 MySQL 的从库，监听数据库底层的变更日志，秒级推给 ES。        | 准实时（毫秒级）；**对业务代码零侵入**（业务代码只管写 MySQL）。 | 架构极其复杂，需要运维 Canal 和 MQ，成本极高。                                | 大型互联网公司、高并发、要求实时搜索的场景。   |
| **MQ 异步**                       | 业务代码里发个消息到 Kafka，有个专门的消费者去更新 ES。             | 解耦；支持失败重试；能削峰填谷。                                 | 引入了新的中间件（MQ），系统复杂度变高。                                      | 中大型系统。                                   |


**面试官问：“既然你们项目用了定时同步，那如果是双写，你们应该先写 MySQL 还是先写 ES？”**

**你的满分回答**：

> “**必须绝对先写 MySQL（主库）！**
> 因为 MySQL 是唯一真相来源（Source of Truth）。如果先写 ES 成功了，但写 MySQL 时网络超时失败了，那 MySQL 里没数据，ES 里却多了一条脏数据，这就变成了‘幽灵数据’，极难排查。
> 先写 MySQL，哪怕后面写 ES 失败了，我们也可以通过定时任务或者补偿机制，把 MySQL 里的真实数据再次同步给 ES，从而保证**最终一致性**。”



### `bool query` 的四个格子

1. **`must`（必须匹配）**：装进这里的条件，文档**必须**满足。相当于 SQL 里的 `AND`。
   * *特殊能力*：**会计算相关度得分（`_score`）**。
2. **`filter`（必须匹配，但不打分）**：装进这里的条件，文档**必须**满足。也相当于 SQL 里的 `AND`。
   * *特殊能力*：**绝对不计算得分，且会被 ES 自动缓存，速度极快！**
3. **`should`（应该匹配）**：装进这里的条件，文档**最好**满足。相当于 SQL 里的 `OR`。
   * *特殊能力*：满足的条件越多，得分越高。通常配合 `minimum_should_match` 参数（比如至少满足 1 个）。
4. **`must_not`（必须不匹配）**：装进这里的条件，文档**绝对不能**满足。相当于 SQL 里的 `!=` 或 `NOT`。
   * *特殊能力*：不计算得分。
